# Dependencies (GATE-08 record)

Every dependency in this project is **pinned to an exact version**, no caret or tilde
ranges. Two reasons: the spec requires reproducible builds, and behaviour that is
measured on this hardware must stay measured. Upgrading anything here requires re-running
GATE-08 (build + flash + the affected tests) and recording the result in this file.

Version evidence below was read from the authoritative registry metadata on
**2026-10-16** (Android artifacts from `dl.google.com`/Maven Central `maven-metadata.xml`,
firmware libraries from the PlatformIO registry API, Gradle from `services.gradle.org`).
Nothing in this table is recalled from memory.

### Generator provenance: use the library's, never a pip copy

The nanopb **generator** is taken from `firmware/.pio/libdeps/*/Nanopb/generator/` -
the library PlatformIO already downloaded for the firmware, rather than from PyPI.
Two reasons, one of which was hit while implementing this:

1. **Version agreement is structural.** The generator and the decoder that ships in the
   binary come from the same directory, so the generator can never emit an option the
   decoder does not understand. A pip-installed generator is a separate version
   negotiation that will silently fail one day.
2. **The documented pin does not exist on PyPI.** `pip install nanopb==0.4.9.2` fails:
   PyPI's newest stable is `0.4.9.1`, then `1.0.0.dev*`. The PlatformIO registry reports
   `0.4.92` for the same release. An earlier revision of this table recorded the
   nonexistent PyPI pin, `tools/gen_proto.py` now uses the bundled generator, so the
   table no longer depends on a version string that cannot be resolved.

Consequence: `tools/gen_proto.py` requires `pio run` to have been executed at least once
(and says so, with the command, if it has not).

### Java codegen is delegated to Gradle, not to `protoc` here

`grpc_tools.protoc` (1.84.0 / libprotoc 35.1) is built **without Java codegen**: it
accepts no `--java_out`, and nanopb's own `protoc` shim delegates to it, so the Android
side cannot be generated by a local `protoc`. The Android build therefore generates the
javalite sources itself through `com.google.protobuf` Gradle plugin `0.10.0`, which
pulls a protoc that does include Java. `tools/gen_proto.py` reports that side as
`DEFERRED` with the reason instead of pretending it ran.

### Known risk: NimBLE 2.5.1 against the Arduino core version

The PlatformIO platform pins an Arduino core, and NimBLE-Arduino's release notes document
fixes for specific Arduino **3.x** core combinations while the platform ships a **2.0.x**
line. No maintainer-published compatibility matrix exists for the exact pair, so this is
treated as an open GATE-05 question rather than assumed to work: M3 must compile and run
the BLE peripheral on the physical board before anything depends on it. If it fails, the
DEC-05 fallback is Bluedroid.

Verified on this host: the installed framework package is
`framework-arduinoespressif32 @ 4.20017.260907` (Arduino-ESP32 core 2.0.17), observed via
`pio pkg list -g`, alongside `toolchain-xtensa-esp32 @ 8.4.0+2021r2-patch5`. The
dependency graph and the exact library versions resolved by the build are captured in
the build log, and the flash/RAM figures are in
[docs/VERIFICATION.md](VERIFICATION.md) and [docs/HARDWARE_REPORT.md](HARDWARE_REPORT.md).

## 3. Deviations from "latest stable"

DEC-09 says `compileSdk`/`targetSdk` should be *the latest stable API level at project
start*. Three pins deviate from the newest available, each for a measured, recorded reason.

### D-01, compileSdk 36, not 37; Compose BOM 2026.06.01, not 2026.09.00

* **What:** the newest stable Compose BOM (`2026.09.00`) pulls Compose 1.12, which requires
  `compileSdk 37`. The build uses `compileSdk 36` with BOM `2026.06.01`.
* **Why:** the SDK installed and licensed on this host is `platforms;android-36` with
  `build-tools;36.0.0`. Raising compileSdk would require installing and licensing a new
  platform, and would also force the AGP 9 line (see D-02).
* **Evidence:** `docs/evidence/GATE-01-setup-check.txt` records the installed platform;
  the AAR-metadata error text is preserved in `docs/evidence/GATE-08-android-build.txt`
  if a future upgrade attempt hits it.
* **Impact:** none on shipped behaviour. Compose 1.10/1.11-era APIs cover everything the
  UI uses. Revisit when the project moves to an SDK 37 host.

### D-02, AGP 8.13.2, not 9.4.1

* **What:** the newest AGP stable is 9.4.1; the build pins 8.13.2.
* **Why:** AGP 9 enables **built-in Kotlin**, and its new DSL is documented as not
  compatible with applying the `org.jetbrains.kotlin.android` plugin by default. The
  project's build files follow the documented Kotlin-plugin setup that the spec's tests
  and the module layout are written against. Adopting AGP 9 would mean reworking the
  build scripts, which is not the change the spec asked for.
* **Evidence:** AGP release notes (built-in Kotlin / migration path) recorded in
  `docs/evidence/GATE-08-dependency-versions.txt`.
* **Impact:** we stay on the 8.x line, which is supported for API 36 and receives security
  fixes. Revisit deliberately, not incidentally.

### D-03, Kotlin 2.3.21, not 2.4.21

* **What:** newest stable Kotlin is 2.4.21; the build pins 2.3.21.
* **Why:** Room needs KSP, and KSP's newest published version is **2.3.12**, which pairs
  with Kotlin 2.3.x. Using Kotlin 2.4.21 would leave the annotation processor without a
  matching release.
* **Evidence:** `com.google.devtools.ksp:symbol-processing-gradle-plugin` metadata (160
  versions, newest `2.3.12`).
* **Impact:** none for the code this project writes. Unpin when KSP publishes a 2.4.x line.

## 4. How to reproduce this list

```bash
# Android: the authoritative version lists
curl -s https://dl.google.com/dl/android/maven2/androidx/compose/compose-bom/maven-metadata.xml
curl -s https://repo1.maven.org/maven2/com/google/devtools/ksp/symbol-processing-gradle-plugin/maven-metadata.xml

# Firmware: the PlatformIO registry
curl -s https://api.registry.platformio.org/v3/packages/h2zero/library/NimBLE-Arduino
curl -s https://api.registry.platformio.org/v3/packages/platformio/platform/espressif32
```

Run `python tools/check_dependency_pins.py` to assert that `platformio.ini` and
`libs.versions.toml` still contain exactly the versions recorded here.
